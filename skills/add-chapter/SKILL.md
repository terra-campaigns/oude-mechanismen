# Add Chapter

Create and integrate a new chapter or session log into the campaign chronicles.

## 1. Intake & Clarification

If the user's prompt does not supply all required details, ask clarifying questions before writing:

1. **Campaign**: Which campaign does this chapter belong to?
   - Check available subfolders in `campaigns/` (or check `Default Campaign Subfolder` in `.agents/AGENTS.md`).
2. **Episode Number & Naming Convention**:
   - Check existing files in `campaigns/<Campaign>/` to determine the filename convention and the next sequential number.
   - Common patterns: `ep_<NNN>.md` (e.g. `ep_011.md`), `<NNN>.md` (e.g. `003.md`), or `chap<NNN>.md` (e.g. `chap002.md`).
3. **Chapter Title**: An evocative title matching the episode's central dilemma, hazard, creature, or event.
4. **In-Universe Date (`nav_order`)**:
   - Date or timestamp of the session in `YYYY-MM-DD` or `YYYY-MM-DD HH:MM` format.
   - Check previous episodes in the campaign to maintain chronological order and timestamp precision.
5. **Region & Location**:
   - Where did the session take place? (e.g. trail station, space station, colony sector, orbital facility).
   - Use `region:` or `location:` in front matter according to the campaign's established pattern.
6. **Hub / Base / Caravan Index**:
   - Which central index should be linked in the comment block? (Check `Campaign Hub Page` in `.agents/AGENTS.md`).
7. **Session Notes or Archival Notes**:
   - Raw player actions, discoveries, trades, NPC interactions, debts, and mechanical consequences.
   - Or an existing structured notes file generated by `scribe-session` in Google Drive (e.g. `<drive_dir>/_sessions/<slug>_session_notes.md`).

## 2. Entity Resolution & Cross-Linking

Before drafting the chapter prose:

1. **Identify mentioned entities**: Scan the session notes for all PCs, NPCs, factions, locations, and creatures.
2. **Search Directory**: Consult `.agents/context/catalog.json` (or use `rg`) to locate the exact filenames and paths in `directory/`.
3. **Format relative links**: Ensure every entity is linked on its first significant mention using relative paths (e.g. `[Kur (Barista)](../../directory/Atles/Barista.md)`, `[Brightside Station](../../directory/Perdurabo/BrightsideStation.md)`).
4. **Clarify new connections**: If a new relationship between characters or factions emerges during the session, prompt the user for the specific relationship dynamic and whether to document it bidirectionally.

## 3. Template & Front Matter

Create the file in `campaigns/<Campaign>/` following the campaign's filename convention.

### Front Matter Specification

```yaml
---
layout: default
type: session
nav_exclude: false

parent: <Exact title of the campaign index>
title: <Chapter Title>
region: <Region or Location Name> # or location: <Location Name>
nav_order: <YYYY-MM-DD or YYYY-MM-DD HH:MM>
narration: 
footer_content: 

images:

---
```

> [!NOTE]
> - `type:` must be `session`.
> - `nav_order:` must be the in-universe date or timestamp string (`YYYY-MM-DD` or `YYYY-MM-DD HH:MM`). Jekyll uses this to format the date in the chapter header and order episodes chronologically.
> - `narration:` is an optional list of character names if dedicated individual narrative sub-logs exist (e.g. `ep_011_Pilik.md`). Leave empty if none.

### Scaffolding & Comment Block

Immediately following front matter:

```markdown
{% include header_chapter.md %}
{% comment %}
`=map(this.images, (x) => "![im|200](" + x + ")")`
```dataview
LIST without ID "["+ title + "](" + regexreplace(file.path, ".md", "") + ")" + ", from " + regexreplace(file.folder, "^[^\/]*\/", "") FROM ([[]]) OR outgoing([[]]) WHERE file.path != this.file.path SORT file.folder DESC
```
---

- [index](<relative_path_to_hub_or_base_index.md>)

{% endcomment %}
```

> [!NOTE]
> The hub/caravan link inside the comment block ensures Jekyll's `_plugins/data_extractor.rb` builds bidirectional links connecting the base/hub/caravan to this session.

## 4. Structure, Prose Formatting & Voice

Chapter writing must adhere to setting conventions defined in `.agents/AGENTS.md` and follow a semi-strict structural format:

### Structural Rules (Semi-Strict Format)

1. **2 to 4 Subheaders**:
   - Structure the chapter body into 2 to 4 themed subsections using `## Heading`.
   - Always leave an empty blank line immediately following any Markdown heading (`#`, `##`, `###`).

2. **2 to 4 Paragraphs per Subheader**:
   - Each subsection must contain between 2 and 4 distinct paragraphs.
   - Separate distinct paragraphs with a blank line (skip line). Do not combine multiple paragraphs into a single block.

3. **2 to 4 Sentences per Paragraph**:
   - Each paragraph must consist of between 2 and 4 sentences.
   - In Markdown, each sentence must be placed on its own line (one sentence per line).

#### Structure Template Example

````markdown
## First Subheader

First sentence of first paragraph.
Second sentence of first paragraph.
Third sentence of first paragraph.

First sentence of second paragraph.
Second sentence of second paragraph.

## Second Subheader

First sentence of first paragraph.
Second sentence of first paragraph.
Third sentence of first paragraph.
Fourth sentence of first paragraph.

First sentence of second paragraph.
Second sentence of second paragraph.
Third sentence of second paragraph.
````

### Voice & Register

1. **British English**:
   - Use British English spelling and conventions throughout (e.g. *favour*, *travelled*, *rumours*, *armour*).

2. **Setting Register**:
   - Align tone, vocabulary, cadence, and aesthetic descriptions with the setting rules in `.agents/AGENTS.md`.
   - Avoid purple prose or unnecessary flourishing; crisp, evocative prose grounded in concrete sensory details works best.

3. **Factual Fidelity**:
   - Stay strictly faithful to the GM's play report.
   - Do not invent plot developments, player character decisions, or unearned successes.

4. **Bilingual Campaigns (e.g. Portuguese / British English)**:
   - When `Chapter Output Format:` in `.agents/AGENTS.md` specifies bilingual output, format the chapter body into two parallel sections:
     ```markdown
     English version below
     {: .text-delta .text-right}

     ## <Primeiro Subtítulo em Português>

     <Parágrafos em Português com links de entidades relativos...>

     ---

     ## <First Subheader in British English>

     <Paragraphs in British English with identical relative entity links...>
     ```
   - Both language versions must adhere to the semi-strict structural format (2–4 subheaders, 2–4 paragraphs per subheader, 2–4 sentences per paragraph, one sentence per line) and share identical entity relative markdown links.

## 5. Pre-Publishing Audit Protocol (The 3-Gate Verification)

Before declaring any chapter, note, or session chronicle ready for publication or PR review, the agent must execute the formal 3-Gate Pre-Publishing Audit and present the standardised readiness scorecard.

> [!IMPORTANT]
> **Token Preservation & Gate Triggering:**
> To preserve LLM context and prevent unnecessary token burn, the full 3-Gate Audit is **NOT** executed on routine intermediate commits. It is strictly mandatory:
> 1. Immediately prior to requesting final operator review or drafting a Pull Request (`gh pr create`).
> 2. Whenever an operator asks *"What is still left before publishing?"* or *"Is this session ready to publish?"*.
> 
> Declaring publication readiness on the basis of Git cleanliness, CI passing, or Jekyll build status alone is strictly prohibited. Deterministic Gate 1 (`lint_chapter.py`) executes 100% locally with zero token consumption and may be run at any time.

### Gate 1: Prose Architecture & Cadence (`scripts/lint_chapter.py`)

Run the deterministic chapter linter across the target file:

```bash
python3 scripts/lint_chapter.py <path_to_chapter.md>
```

*(For bilingual files, pass `--bilingual` if not auto-detected; pass `--format json` for agentic consumption).*

- **Verification:**
  - 2 to 4 subheaders (`## Heading`).
  - 2 to 4 paragraphs per subheader.
  - 2 to 4 sentences per paragraph.
  - Exactly one sentence per line (no inline multiple sentences).
  - Empty blank lines immediately following all headings.
- **Pass Criterion:** Exit code `0` with zero diagnostic errors.

### Gate 2: Tone & Voice Calibration (`review-style`)

Audit the prose against `## Campaign Specification` in `.agents/AGENTS.md`:

- **Verification:**
  - Setting register (e.g. terse industrial cadence, sensory grime, workplace realism).
  - British English spelling throughout (*favour*, *travelled*, *rumours*, *armour*).
  - Strict prohibition of boxed narrative (`> Table Read-Aloud`), conversational monologues, or purple parody.
  - For bilingual campaigns, verify parallel consistency between Portuguese and British English sections.
- **Pass Criterion:** All tone defects polished or explicitly acknowledged by the operator.

### Gate 3: Wiki & Asset Integrity (`lint-wiki`)

Verify static site cohesion and referenced assets:

- **Verification:**
  - All internal relative markdown links resolve to existing files on disk.
  - All referenced image assets exist in `imgs/` or gallery paths.
  - Sequential episode numbering and chronological date (`nav_order`) align with campaign timeline.
  - Tier 1 catalogue compiled cleanly (`ruby --disable-gems _plugins/data_extractor.rb`).
  - Static site builds without Liquid errors (`bundle exec jekyll build`).
- **Pass Criterion:** Zero broken links or missing asset paths.

### Standardised Pre-Publishing Readiness Scorecard

Whenever evaluated, report the audit results in this exact structure:

```markdown
### Pre-Publishing Readiness Scorecard — <Chapter Title>

- **Gate 1 (2-4 Framework, lint_chapter.py):** [PASS / FAIL] — <details / violations>
- **Gate 2 (Tone & Voice, review-style):** [PASS / FAIL] — <details / tone check>
- **Gate 3 (Wiki & Asset Lint, lint-wiki):** [PASS / FAIL] — <details / link & image resolution>
- **Overall Verdict:** [READY / NOT READY]
```

No gate may be reported as `PASS` without its underlying verification check having been executed in the active session. If any gate fails, state the specific remediation steps required.

## 6. Post-Verification Git Hygiene

After achieving an overall verdict of `READY`:

1. Refresh the Tier 1 catalogue: `ruby --disable-gems _plugins/data_extractor.rb`.
2. Confirm the Jekyll build succeeds: `bundle exec jekyll build`.
3. In downstream engineering repositories (`AretePX/*`), commit changes to a dedicated feature branch.
4. In personal life vaults (`~/Repos/arete`), leave modified files unstaged for manual operator review.
5. Once a Pull Request is merged or closed, immediately delete the feature branch locally and remotely to prevent branch sprawl.
